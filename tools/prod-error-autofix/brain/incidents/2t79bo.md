**Outcome.** duplicate of luol15 — MR https://gitlab.com/avada/seo/-/merge_requests/2104

**Root cause.** @avada/core 4.8.2's setSession assumes the decrypted `__session` cookie is an object; when a client presents a `__session` cookie that does not decrypt under the hardcoded key 'avada-session-identifier', CryptoJS's unvalidated PKCS7 unpad occasionally yields a 1-2 char digit string, JSON.parse turns it into a bare number, and the strict-mode assignment `cookies[key] = value` throws "Cannot create property 'shopifyTopLevelOAuth' on number '8'", 500-ing the request inside auth middleware before any controller runs.

**Mechanism.** GET /api/shopify/files (apigen2, Shopify Mobile Android WebView, 0.197s) → api.js mounts createAuthMiddleware → middleware/auth.js:33 → @avada/core verifyToken.js:119 calls setSession(ctx, 1, 'shopifyTopLevelOAuth') after checkIfActiveAccessToken → cookiesHelper.js:15 does decryptText(ctx.cookies.get('__session')) → hashHelper.js:26 JSON.parse(AES.decrypt(...).toString(Utf8)). CryptoJS strips PKCS7 padding by trusting the last plaintext byte without validating it, so garbage plaintext is frequently truncated to 1-2 bytes; when those bytes are ASCII digits, JSON.parse returns a Number instead of an object. cookiesHelper.js:16 then assigns a property on that primitive under 'use strict' → TypeError. The stack in stderr matches these three frames exactly (cookiesHelper.js:16 ← verifyToken.js:119). Reproduced locally against the repo's own node_modules: 26 of 200000 random base64 `__session` values decrypted to bare numbers (0.013%), sample values 0,1,2,3,4,6,7,8,9,21,75 — the same small-integer shape as the six distinct values seen in prod (4,5,7,8,9,33). Failure is endpoint-independent: it fires in the auth layer, so whichever route the browser happens to call 500s.
