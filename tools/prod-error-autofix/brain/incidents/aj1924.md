**Root cause.** The /proxy/* storefront handlers have no request-level deadline: initShopify constructs shopify-api-node without a `timeout`, so the client keeps its 60000 ms default, which is >= the proxy function's own `timeoutSeconds: 60` — a slow Shopify Admin GraphQL call on a cache miss therefore runs until Cloud Run kills the container at 59.99 s and returns 504, and no catch block ever runs.

**Mechanism.** GET /proxy/tags -> tag.controller.js listStorefront -> shopCacheService.withCache (tag.controller.js:76). On a Redis miss the fetchFn calls getTagsForStorefront, whose single upstream call is `await shopify.graphql(getArticleTagsList)` (tag.service.js:176); the /proxy/posts-by-tag twin is getArticlesByTagWithPagination (tag.service.js:246). That client comes from initShopify (shopifyService.js:26), which passes only apiVersion/accessToken/shopName/autoLimit — no `timeout` — so shopify-api-node applies its default `timeout: 60000` (node_modules/shopify-api-node/index.js:65). Cloud Run kills the request at timeoutSeconds: 60 (http.js:60) first, at 59.9938-59.9941 s measured. Because the container terminates the request instead of the promise rejecting, the controller's catch/logger.error never fires — which is exactly what the logs show: all 4 severity>=ERROR entries in the window are run.googleapis.com/requests request logs, zero application lines, stderr read empty. The same code path is visibly slow-tailed on the same instance: two requests completed 200 at 38.783 s and 14.487 s, i.e. the 504s are that distribution crossing 60 s, not a distinct failure mode. Every failing domain also succeeded in the same window (club-piel 2x200, bandai-collectors 6x200, hardpressed-print-studo 10x200, pslfireandsafety-co-nz 4x200), so this is per-call upstream latency on a cache miss, not a broken shop or a wedged instance.
